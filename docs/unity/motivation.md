# 写这套笔记的初衷

这套笔记不是从“如何安装 BepInEx”开始的，而是从一个更具体的问题开始的：**当一款 Unity 游戏用 IL2CPP 编译、又用 HybridCLR 做热更新时，现有的 MOD 教程几乎全部失效。**

把开发过程中反复踩到的坑整理成可以检索的文字，是我写这些页面的直接原因；如果后来的人能少走一次弯路，这些记录就算有价值。

> 本页讲的是“为什么写”，不构成对任何游戏的使用授权。第三方插件可能违反游戏规则，详见[使用风险](unity/safety.md)。
>
> 另外说明一下时效性：下面这些个人经历写于 2026 年 11 月，涉及的游戏时长、版本状态和兼容性进展都会随时间变化，阅读时请以当时的情况为准。

## 入坑：从玩游戏到改游戏

我猜不少人和我一样：一旦真的开始做 MOD，玩游戏的时间反而少了，心思都花在“这个东西是怎么实现的、我能不能改”上。

入坑的理由五花八门——有人想要官方没做的玩法，有人嫌官方产能太低、更新太慢，有人只是想让某个细节顺手一点。我属于后两种都占一点。

在《吉星派对》之前，我唯一做过 MOD 的游戏是 Minecraft。初中玩了一年多之后知道了模组这东西，从此满脑子都是“怎么让游戏多出点新东西”。但那时候我对编程几乎没有概念，只知道“要用代码写一个程序”，也知道 Minecraft 是 Java 写的——然后就在配置开发环境这一步卡了整整几年。论坛、帖子、教程翻了个遍，没有一次成功。

直到高中快毕业，我才跟着一个视频教程把环境配起来。那位 UP 主反复说的一句话是：**先把 Java 学了再来写 MOD，不要通过写 MOD 来学 Java。** 碰壁太多次之后我终于听进去了，花了一个月补基础，才正式入坑。

代价是：从那以后我打开 Minecraft，基本都是在测试 MOD、看更新日志，很少真的在玩。玩了十多年，我甚至没有在生存模式里正经击败过末影龙。但也是从模组开发里，我学到了远多于“怎么玩”的东西，后来还参与过一些团队，现在仍在参与大型模组的开发。

这段经历对我写这份教程的影响很直接：**我知道从零配环境有多劝退，也知道教程只能把人送到门口。**

## 社区里的人

除了参与过一些团队，我还加过各种群聊——做模组的、做工具的、搞逆向的，认识了不少开发者，也和其中一些人合作过。

很多人的技术力让我很佩服：有些问题我卡了一个星期，他们看一眼日志或者反编译结果就能指出方向。这些交流大部分不会写进教程，但它们确实构成了我继续做下去的土壤——知道有人在认真做同一件事，本身就是一种支撑。

## 我为什么会盯上这款游戏

《吉星派对》是一款二次元游戏，玩法相对固定，发布已经两年（这个数字会随版本推进变化）。团队规模不大，产能一直被玩家诟病——这几乎是所有小厂二游的共同处境。

我是今年二月开始玩的。起因很偶然：喜欢的一位主播在和别的主播联动，直播里说之后可能会和粉丝一起玩，我就下载下来想先了解一下。后来她因为各种原因没有再打开过这款游戏，我们始终没能一起玩上一局。说没有遗憾是假的，但她现在还在正常直播，而我也因为这次偶然的下载，走上了一条完全不同的路——这一点我一直挺感谢她。

真正开始玩之后，就一天没断过：到写这段文字时已经接近九个月，每天至少一局。玩得久了，能明显感觉到优化空间很大，于是去官方反馈平台写了一份几千字的建议，把遇到的 Bug、想要的功能和疑问都列了进去。中间有个小插曲：反馈框限制 500 字，我用开发者工具把前端的 `maxlength` 去掉，硬是把几千字提交了上去——至于客服后来怎么回的，我到现在也没去看。

不过“想改”和“开始改”之间隔了好几个月。玩到第二个月左右，我匹配到的队友里有人操作快得不像手速，这才意识到游戏也有脚本。最初的想法很朴素：**别人能写，我是不是也能写一个。**

真正动手又往后拖了一段时间，原因有两个：一是工作占掉了时间；二是当时能找到的补丁只保证“能让游戏跑起来”，并不保证能在这之上加载别的东西。换句话说，路是通的，但只能走一个人、带不了行李。

那时候我还不了解游戏的框架，以为脚本就是“把 DLL 注入进去”。我确实把注入跑通了，但没有任何想要的效果——不过至少学会了注入是怎么回事。接着我又去试调试、看反汇编，说实话并不太会，只是有样学样，也没找到想改的方法。

再后来才知道有 BepInEx 这种东西，能给 Unity 游戏写插件。我照着教程装，结果怎么都跑不起来，偶尔跑起来也是各种报错。直到我去翻游戏目录里导出的一堆 DLL，才意识到一件关键的事：**游戏的代码并不在 `GameAssembly.dll` 里。**

它用了 HybridCLR 做热更新。

顺着这条线继续查资料，结果和前面说的一样：几乎没有。能搜到的教程全是 BepInEx 5 + Mono 那一套，IL2CPP + HybridCLR 的完整流程一篇都没有。我刚入坑 Unity MOD，就撞上了一个前人没怎么走过的东西。

再往后，兼容性修复出现了，能真正把插件加载起来的构建也出现了，我才算正式动手。能走到这一步，很大程度上是赶上了社区里有人先把路修通。

## 为什么拿《吉星派对》当例子

理由很私人，也很实际。

除 Minecraft 之外，它是我唯一还在长期玩的游戏，而且从今年二月到现在几乎每天都会上线。**只有长期玩，才知道哪些地方真的硌手**——不是“这个功能看起来可以加”，而是“每次都要多点三下，烦”。MOD 的选题如果脱离真实使用，很容易做出一堆没人会开的开关。

另一个原因和游戏本身有关：它出自一个规模不大的团队，产能有限。更新频率、内容量、细节打磨都不可能像大厂那样铺开。这恰恰是 MOD 能补位的地方：

- 界面与交互的细节改进；
- 统计、回放、提示这类“应该有但没有”的辅助功能；
- 本地化、快捷操作等体验补丁。

这不是要替开发者做游戏，而是**在自己玩的那一份里，把想要的东西补上**。长期在线还有附带好处：游戏会持续更新，而每次更新都是一次真实的兼容性测试。补丁能不能活过版本更新，比任何演示都更有说服力。

## 我能贡献的那一份

喜欢一款游戏久了，总会想为它做点什么。

有财力的玩家会充值，支持游戏继续运营；有美术或剪辑能力的玩家会做二创，让更多人看到它；而我两样都不太行，唯一拿得出手的是编程。那就写 MOD：给游戏加一点新内容，改掉一些别扭的地方，让它更好玩一点。

这件事对我来说还有另一层意义：我的工作几乎与编程无关，业余时间做 MOD，让我在某种意义上也参与了游戏开发。学到的新技术、踩过的坑、最后跑起来的那一刻，大概就是编程最让人上瘾的地方。

## 先看文件，再进游戏

说个可能有点奇怪的个人习惯：现在遇到一款体量比较大的游戏，我的第一反应往往不是打开它，而是先看看安装目录里有没有特别大的文件，猜里面存了多少高质量资源，然后想该怎么解包。

以前不一定这样，现在几乎成了条件反射。这个习惯让我对资源结构、打包方式和资源更新流程比较敏感，也解释了为什么这套笔记里资源层的内容占了不小篇幅——很多问题还没进到代码，就已经卡在“东西到底放在哪”上了。

但资源替换终究只是表层。真正让我愿意长期投入的，还是代码。

## 为什么偏向代码型 MOD

我更喜欢编程，这一点没什么好掩饰的。

市面上很多 MOD 本质上是资产替换：换模型、换贴图、换音频，很少碰代码。这类 MOD 的价值不低，但它对美术和素材的要求远高于编程，也不是我最擅长的事。

我更想做的是代码层的东西：改行为、加界面、做统计、补交互。它能真正给游戏增加功能，而不是只换一层皮；也能体现技术力——不是“把文件换掉”，而是“让程序按我的想法跑”。

这也是这套笔记选择 BepInEx 框架路线、而不是只讲资源替换的原因：**资产层解决“看起来不一样”，代码层解决“用起来不一样”。**

## 教程只能领进门

即使是我更熟悉的 Minecraft 模组开发，很多功能也得靠自己摸索。

那些 API 大多是第三方社区做的，做法是在游戏源码里 hook；你只能看到被改动的地方有注释，不可能有人把每个方法都解释清楚——别人没有义务给模组开发者“喂饭”。所以实际开发中，即便你对玩法和机制已经很熟，还是得找到实现代码，去猜它到底做了什么。

Minecraft 有十几年的历史、几十万个模组，你想做的东西大概率早有人做过类似的，因此资料相对充足。我参考过各种文字和视频教程，也翻过几百份模组源码——相对于总量只是皮毛，但确实提供了很多思路。

即便这样，碰到偏门功能时还是只能硬啃：要么没人做过，要么有人做过但没写教程，或者教程只讲步骤不讲原理。**但这种时候，做出来的东西就是首创，等于替后来的人把路先走了一遍。**

HybridCLR 这边更极端：连“前人做过的类似功能”都很少，很多时候不是“找一份源码参考”，而是“先确认这条路走不走得通”。

说到底就是那句老话：师傅领进门，修行靠个人。前人也是在几乎没有资料的情况下探出来的路，我们能做的是站在他们的肩膀上，再往前走一点。

## 网上能找到的教程，其实停在另一个时代

按目前公开可查的资料，Unity 游戏的 MOD 教程大致分三代，而这三代之间并不是平滑过渡的：

| 阶段 | 常见写法 | 为什么对 HybridCLR 游戏无效 |
|---|---|---|
| Mono 时代 | 安装 BepInEx 5 → 用 dnSpy 打开 `Assembly-CSharp.dll` → 改 IL 或挂 Harmony | 游戏根本没有可供 JIT 执行的 `Assembly-CSharp.dll`，逻辑已经 AOT 化 |
| IL2CPP 早期 | 使用 BepInEx 5 的社区魔改版，或手工注入 `GameAssembly.dll` | 缺少统一框架，维护成本高，且多数文档已经过期 |
| BepInEx 6 | 使用 `Unity.IL2CPP` 构建 + Il2CppInterop 生成代理程序集 | 方向正确，但发行版不认识被 HybridCLR 改造过的运行时 |

实际情况是：**国内和国外的教程都集中在 Mono 框架上**，IL2CPP 的内容本来就少，而且其中相当一部分还停留在 BepInEx 5 的术语和工具链里；至于 HybridCLR，中文资料里能查到的系统性文章，基本只有[知乎上的这一篇](https://zhuanlan.zhihu.com/p/1962949427217015984)（作者 Xkein）。

这篇知乎文章的价值在于它第一次把问题讲清楚了：HybridCLR 改变了 IL2CPP 的元数据和方法执行方式，因此不能沿用普通 IL2CPP 的 Hook 思路。SNWCreations 正是沿着这个思路，做出了 [Il2CppInterop PR #251](https://github.com/BepInEx/Il2CppInterop/pull/251) 的修复，并把它拆成了可以单独引用的 [IL2CppSharp](https://github.com/SNWCreations/IL2CppSharp) 与 [IL2CppSharp.Hooking](https://github.com/SNWCreations/IL2CppSharp.Hooking)。

具体到例子：Mono 时代的《Cities: Skylines》靠 BepInEx 5 加载 *TM:PE*、*Move It* 这类模组；IL2CPP 时代的《Among Us》《Lethal Company》已经转向 BepInEx 6 + Il2CppInterop；而 HybridCLR 在国内商业游戏里早就是常规方案——按官方统计，头部 Unity 热更新游戏里约 25%–35% 使用它。完整的生态梳理、代表作品和经典 MOD 见[Unity MOD 生态](unity/ecosystem.md)。

## 社区里的“魔改”，走的是另一条路

既然框架这条路这么难走，现存的魔改内容自然选择了另一条路：**直接修改热更新文件本身，再通过 DLL 注入加载。**

这条路能跑通，也很直接，但它有几个绕不开的代价：

- 每次游戏更新热更新程序集，补丁就要重做一次；方法签名一变，旧补丁立刻失效。
- 多个修改很难共存——大家都在改同一份 DLL，冲突只能靠人工合并。
- 出问题时没有日志、没有断点，只能在“能启动 / 不能启动”之间二分。
- 分发出去的往往是整包修改后的文件，用户无法只挑其中一项功能。

这不是在批评这种做法：在没有可用框架的时候，它就是唯一可行的做法。但它不应该成为**唯一**的做法。

## 所以这套笔记想补的是哪一块

我想记录的是“框架路线”，也就是：**让 BepInEx 6 在 HybridCLR 游戏里稳定启动，然后在运行时访问、调用、Hook 热更新代码。** 它比改 DLL 麻烦得多，但它是可组合、可更新、可调试的那条路。

具体来说，有三个目标：

1. **把“空插件能启动”变成一个独立的、可复现的检查项。** 很多教程一上来就讲 Hook，但在这个组合里，宿主能不能起来本身就是一个需要单独验证的关卡。
2. **把坑写成“现象 → 原因 → 动作”。** 单纯的结论记不住，能对应到日志和代码位置的结论才有用。
3. **只写可以公开验证的部分。** 公开的资料、开源库的行为、自己项目里可复现的工程问题；不涉及游戏文件、不涉及绕过检测。

## 需要先说清楚的三个前提

- **“能编译”不等于“能运行”。** 项目里引用了正确的 NuGet 包，只说明编译期类型齐全；运行时崩溃往往发生在插件加载之前，属于宿主层的问题。
- **“能找到方法”不等于“能 Hook”。** 反射拿得到 `MethodInfo`，不代表这个方法是 AOT 编译的、可以由 Harmony 直接替换。
- **“我这儿能用”不等于“所有人都能用”。** 修复主要在一款游戏、一个 Unity 版本上验证过，HybridCLR 的版本差异、`MethodInfo` 的布局差异都会影响结果。

## 这些经验是从哪来的

本站的结论来自一个仍在开发中的 MOD（AstralProbe）及其配套 SDK 的长期迭代。它们不是一次性写出来的设计文档，而是在真实崩溃、真实日志和真实版本更新里逐步修正的结果。

所以有些页面读起来会显得“啰嗦”——那些反复出现的注意事项，通常都对应过一次实际的故障。

## 框架不是天生的

Minecraft 的模组生态也不是一开始就这么方便。

最早只是少数开发者在游戏里做 hook，自己攒出最初的框架；社区慢慢变大之后，框架被不断修补、扩展，才有了今天“装个加载器就能写插件”的体验。更难得的是，官方后来也逐步承认了模组的存在：有模组作者加入 Minecraft 团队之后（Dinnerbone 在加入 Mojang 之前就是模组开发者），官方还公开了方便开发者使用的混淆映射表。

这段历史对我的影响很直接：**我很幸运，最早接触的就是一个能从代码层面开发 MOD 的游戏**，也因此真正了解了计算机编程——尽管现在的工作和编程无关。

## 为什么还是想把它写下来

说到底，这款游戏只是一个小厂作品。坦白讲，它还能运营多久，我并不知道。版本节奏、团队变动、运营策略，任何一项变化都可能让今天能用的补丁明天就失效。

但至少，它让 HybridCLR + IL2CPP 的游戏 MOD 开发多了一条实际走过的路，而不只是“理论上可行”。

我当然希望它能一直运营下去，也希望这套教程能一直完善：让后来的人少踩一次坑，也希望能让官方看到——在不妨碍公平性的前提下，第三方插件有时只是玩家表达“我还想继续玩”的一种方式。

关于 AstralProbe 本身，也说清楚一点：它现在没有完整公开，里面确实有一些不方便放到台面上的调整。但后面我仍然会逐步公开它的源码——哪些能公开、哪些暂时不能，我会按这个标准来取舍。

这不是发一份公告、然后让玩家拿去随便用。比起“又多了一个能改游戏的东西”，我更希望官方能因此更重视玩家社区的影响——哪怕它只是一个小厂游戏。因为社区里存在的并不只有脚本：还有大量功能优化、Bug 修复，以及官方一直没顾上的细节。这些东西如果只能以“外挂”或“私改”的形式存在，对谁都不算好事。

## AI 帮我把想法变成了代码

还有一件事值得单独说：这个 MOD 能走到今天，很大程度上得益于这两年的 AI 技术。

有些想法我很早就有，但以自己的工程能力，可能要花几倍时间才能落地；AI 让我能先把东西跑起来，再一点点修正。AstralProbe 最初的框架、第一次成功加载，以及很多原本不知道从哪下手的 API 调用，都是在反复对话和试错里完成的。

当然，AI 给的是起点，不是答案：它写出来的东西必须自己读、自己验证，崩溃也不会因为“是 AI 写的”就网开一面。但至少，它让“一个人也能做出一个像样的 MOD”从愿望变成了现实。

## 写给开发者和玩家

**如果你也在做，或者正打算做 MOD：**

- 先把“能启动”当成一个独立目标，别急着写功能；
- 出问题时先记录版本、日志和复现步骤，再动代码；
- 别人的源码是最好的教材，但别指望它替你解释一切；
- 如果这条路没人走过，你踩的每个坑都值得写下来——它可能比功能本身更有价值。

**如果你只是玩家：**

- MOD 不等于外挂，绝大多数作者只是想让游戏更顺手一点；
- 用之前先看它改了什么、会不会影响联机公平；
- 遇到问题先看说明和日志，作者通常比谁都想知道哪里坏了；
- 喜欢某个 MOD 的话，一句具体的反馈比“支持”有用得多。

这页写的是我自己的经历，不一定适合每个人。但如果它能让你少一点“我是不是不适合做这个”的怀疑，那它就没白写。
