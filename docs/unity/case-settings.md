# 案例四：设置面板与配置

**目标**：让用户能改 MOD 的行为——既能用 BepInEx 的 `.cfg` 兜底，也能在游戏里点开一个“看起来像原版”的设置页。

这是整个 MOD 里最容易返工的部分。原因很简单：**“能写出一个窗口”和“让这个窗口在游戏里活下来”是两件事。**

## 一、先选路线

| 方案 | 优点 | 代价 |
|---|---|---|
| BepInEx `ConfigFile` | 跨版本稳定、可手改、出问题容易回滚 | 体验割裂，用户要退出游戏改文本 |
| 原生设置页（克隆原版控件） | 体验统一，可即时生效 | 依赖原版资源包、布局与动画，游戏更新容易坏 |
| 独立悬浮窗（自绘） | 不依赖原版设置页 | 需要自己处理层级、遮挡、输入穿透 |

常见做法是**两条都保留**：关键开关用 `Config.Bind` 持久化，原生设置页只是它的一个前端。

```csharp
var enabled = config.Bind("General", "EnableOverlay", true, "是否显示对局覆盖层");
var fontSize = config.Bind("UI", "FontSize", 18,
    new ConfigDescription("字号", new AcceptableValueRange<int>(12, 32)));
```

## 二、原生设置页的五个教训

### 1. 不要把原版页面当容器

原版的“屏幕设置”“音量设置”页面自带 Controller、Gear 和资源布局。把 MOD 控件塞进去，`SetVisible` 不代表你的控件会显示；页面切换、动画和滚动都可能把布局重置。

正确做法：**只借样式（标题、分组框、行控件），自建一个视口。**

### 2. 滚动要用原生的

想把页面做成可滚动的，最省事的方案是原版 `ScrollPane` + `GScrollBar`。不要试图“旋转一个滑块”来模拟滚动条——它没有裁剪，也没有滚轮行为。

### 3. 复用控件要整行复用

原版的按键行是“标签 + 输入控件”组合。只复制输入控件、自己另建标签，会出现两套字号、两套间距；把原版控件搬到新的父容器里，滚动时分组框会脱位。

### 4. 新页面没有现成动画

原版 `SettingWindow.SwitchTab` 只给已有页面播动画。你新增的分页需要自己补一段短促的滑入渐显（约 0.3 秒），并且不要留下长期 Tween，否则反复切页会叠加。

### 5. 关闭时要释放

设置窗口关闭后，MOD 创建的滚动容器如果没有释放，下次进入时滚动位置和分组框会错位。释放要挂在关闭回调上，而不是“下次打开时重建”。

## 三、让配置“改坏了也能用”

配置是用户能直接编辑的文件，必须假设它会被写坏。

- **范围校验**：越界值回退到默认，不要直接应用。
- **结构校验**：布局文件缺键时保留上一份有效内容，不要用半套参数重建界面。
- **失败日志**：明确写出“哪个键非法、用了什么默认值”，否则用户只会看到“界面乱了”。

项目里把布局参数外置成独立文件，运行时检测修改并热重载；同时加了完整性检查与数值范围校验，写坏一个值只会让那一项回退，不会把整页布局搞崩。

## 四、本地化：键名也是接口

翻译键一旦写进配置文件或语言文件，改名就是破坏性变更。

- 用点分命名空间（如 `astralparty.settings.ui.title`），不要用中文原文当键；
- 通用键不要带某个 MOD 的专属前缀，否则 SDK 会被绑死在一个 MOD 身上；
- 缺键时回退到内置语言，而不是把 `astralparty.xxx` 直接显示出来。

## 五、旧配置要迁移，不要覆盖

版本升级后，旧键可能还在用户目录里。做法是：

1. 新键先绑定默认值；
2. 首次运行时检测旧键存在，把值导入新键，并写一个迁移标记；
3. 不删除旧节，避免用户降级时丢配置。

## 检查清单

- [ ] 关键开关有 `.cfg` 兜底，可手改
- [ ] 没有把原版设置页当容器
- [ ] 滚动使用原生 `ScrollPane`
- [ ] 复用控件是整行复用
- [ ] 新增分页自己补动画，且不残留 Tween
- [ ] 关窗时释放自建容器
- [ ] 配置有范围与完整性校验，坏值回退
- [ ] 翻译键是点分的，缺键有回退
- [ ] 旧配置有迁移路径
